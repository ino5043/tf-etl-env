## 1. 品質次元分析（6次元）

生産実績データに対して、データ品質の 6 次元すべてを検証する。各次元ごとの具体的なルールと検証方法を以下に定義する。

| # | 品質次元 | 対象 | ルール概要 | 重要度 | 検証タイミング |
|---|---------|------|-----------|--------|-------------|
| 1 | 完全性 (Completeness) | 全 13 カラム | 必須カラムの NULL/NaN チェック。主キー構成要素は 0% 許容 | 高 | Bronze → Silver |
| 2 | 正確性 (Accuracy) | 数量・センサー値 | 範囲チェック（温度 20-80℃、振動 0.1-5.0 mm/s）、マスタ照合 | 高 | Bronze → Silver |
| 3 | 一貫性 (Consistency) | カラム間関係 | 実績+不良 <= 計画*1.1、不良 <= 実績、ステータス整合 | 中 | Silver → Gold |
| 4 | 適時性 (Timeliness) | created_at | データ鮮度 24 時間以内、AM 8:00 JST までに Silver 到達 | 高 | Bronze → Silver |
| 5 | 一意性 (Uniqueness) | 複合主キー | production_date + line_id + product_code + shift で一意 | 高 | Bronze → Silver |
| 6 | 有効性 (Validity) | Enum・フォーマット | ステータス 4 区分、シフト 2 区分、ID フォーマット検証 | 中 | Bronze → Silver |

## 2. 次元別の詳細ルール

### 2.1 完全性 (Completeness)

必要なデータが欠けていないかを検証する。

| カラム | NULL 許容率 | 理由 |
|--------|-----------|------|
| production_date | 0% | 主キー構成要素 |
| line_id | 0% | 主キー構成要素 |
| product_code | 0% | 主キー構成要素 |
| shift | 0% | 主キー構成要素 |
| status | 0% | 設備状態の判定に必須 |
| created_at | 0% | 鮮度チェックに必須 |
| planned_quantity | 1% | 計画未入力のケースを限定的に許容 |
| actual_quantity | 1% | 集計途中のケースを限定的に許容 |
| equipment_id | 1% | 設備マスタ未登録のケースを限定的に許容 |
| defect_quantity | 2% | 検査未完了時に欠損する可能性 |
| operator_id | 5% | 無人運転ラインでは NULL |
| temperature | 5% | IoT センサー欠測 |
| vibration | 5% | IoT センサー欠測 |

**日次レコード件数チェック**: 500〜1,500 件の範囲であること。範囲外は MES 側の異常を示唆する。

### 2.2 正確性 (Accuracy)

データが現実世界の値を正しく反映しているかを検証する。

**範囲チェック**

| カラム | 最小値 | 最大値 | 単位 | 逸脱時の意味 |
|--------|-------|--------|------|-------------|
| planned_quantity | 0 | 100,000 | 個 | 入力ミスまたはマスタ設定誤り |
| actual_quantity | 0 | 100,000 | 個 | カウンター異常またはデータ入力ミス |
| defect_quantity | 0 | 100,000 | 個 | 検査装置の異常 |
| temperature | 20.0 | 80.0 | ℃ | 設備の過熱または冷却異常 |
| vibration | 0.1 | 5.0 | mm/s | ベアリング摩耗、回転体の偏心 |

**マスタ照合**

| ファクトカラム | 参照マスタ | 不一致時の対応 |
|-------------|-----------|-------------|
| line_id | master.production_lines | quarantine に隔離 |
| product_code | master.products | quarantine に隔離 |
| equipment_id | master.equipment | quarantine に隔離 |
| operator_id | master.operators | NULL は許容、非 NULL で不一致は隔離 |

### 2.3 一貫性 (Consistency)

複数カラム間で矛盾がないかを検証する。

| ルール名 | 条件式 | 重大度 |
|---------|--------|--------|
| 実績・不良数量の整合性 | `actual_quantity + defect_quantity <= planned_quantity * 1.1` | Warning |
| 不良数量は実績以下 | `defect_quantity <= actual_quantity` | Critical |
| 実績は計画の妥当範囲内 | `actual_quantity <= planned_quantity * 1.5` | Warning |
| 異常ステータスとセンサー値 | ステータス「異常」なら温度 or 振動が正常範囲外であること | Info |

### 2.4 適時性 (Timeliness)

データが期待される時間内に利用可能かを検証する。

| チェック項目 | 基準 | 備考 |
|------------|------|------|
| データ鮮度 | `created_at` が 24 時間以内 | 最新レコードで判定 |
| Silver 到達 SLA | AM 8:00 JST | 最大 2 時間遅延を許容 |
| データ日付整合 | `production_date` に前日日付が存在 | 日次バッチの正常完了を確認 |

### 2.5 一意性 (Uniqueness)

データに意図しない重複がないかを検証する。

| チェック項目 | キーカラム | 重複時の対応 |
|------------|----------|-------------|
| 複合主キー一意性 | production_date, line_id, product_code, shift | 古いレコードを正とし、新しい方を reject |
| 近似重複検出 | line_id, product_code + 5 分以内 | 警告ログ出力、手動確認を促す |

### 2.6 有効性 (Validity)

データが定義されたフォーマットやルールに従っているかを検証する。

**Enum 値チェック**

| カラム | 許可値 |
|--------|-------|
| status | 正常, 警告, 異常, 停止 |
| shift | 日勤, 夜勤 |

**フォーマットチェック**

| カラム | パターン | 例 |
|--------|---------|-----|
| production_date | `YYYY-MM-DD` | 2026-03-15 |
| line_id | `LINE-NNN` | LINE-001 |
| product_code | `AA-NNNN` 〜 `AAAA-NNNNNN` | AB-1234 |
| equipment_id | `EQ-AA-NNNN` | EQ-ML-0001 |
| operator_id | `OP-NNNNN` | OP-00123 |

## 3. 品質ゲート設計

パイプラインの各レイヤー遷移時に品質ゲートを設置する。ゲートを通過しないデータは次のレイヤーに進めない。

### 3.1 Bronze → Silver ゲート（スキーマ + 完全性）

Bronze レイヤーの生データを Silver レイヤーに昇格させる際の品質ゲート。

```
Bronze (raw CSV)
  │
  ├─ [Gate 1] スキーマ検証
  │     ├── カラム数が 13 であること
  │     ├── カラム名が定義と一致すること
  │     └── データ型が変換可能であること
  │
  ├─ [Gate 2] 完全性チェック
  │     ├── 主キー構成カラム (4列) の NULL チェック → NULL は reject
  │     ├── 必須カラムの NULL 率チェック → 閾値超過は quarantine
  │     └── レコード件数チェック → 範囲外は警告
  │
  ├─ [Gate 3] 一意性チェック
  │     └── 複合主キーの重複排除 → 重複レコードは quarantine
  │
  ├─ [Gate 4] 有効性チェック
  │     ├── Enum 値チェック → 不正値は quarantine
  │     ├── フォーマットチェック → 不正フォーマットは quarantine
  │     └── 型チェック → 変換不能は quarantine
  │
  ├─ [Gate 5] 適時性チェック
  │     └── データ鮮度チェック → 24 時間超過は警告
  │
  ▼
Silver (cleansed Delta Table)
```

**通過条件**: 正常レコード率 >= 90%（エラー率 10% 未満）

### 3.2 Silver → Gold ゲート（全 6 次元）

Silver レイヤーのクレンジング済みデータを Gold レイヤーに昇格させる際の品質ゲート。6 次元すべてを検証する。

```
Silver (cleansed)
  │
  ├─ [Gate 6] 正確性チェック
  │     ├── 範囲チェック（数量、温度、振動）
  │     └── マスタ照合（ライン、製品、設備、作業者）
  │
  ├─ [Gate 7] 一貫性チェック
  │     ├── 実績+不良 <= 計画*1.1
  │     ├── 不良 <= 実績
  │     └── ステータスとセンサー値の整合性
  │
  ├─ [Gate 8] 品質スコア算出
  │     ├── 6 次元の加重平均スコアを算出
  │     ├── グレード判定（A〜F）
  │     └── グレード D 以下でパイプライン停止
  │
  ▼
Gold (business-ready Delta Table)
```

**通過条件**: 品質スコア >= 70（グレード C 以上）

## 4. 異常検知パターン

製造 IoT データに特有の異常パターンを定義し、早期検出を行う。

### 4.1 温度スパイク検出

設備温度の急激な上昇を検出し、設備故障や冷却系統の異常を早期に発見する。

| パラメータ | 値 | 説明 |
|-----------|-----|------|
| 検出方法 | Z-score | 過去 30 日の平均・標準偏差からの乖離 |
| 警告閾値 | Z > 2.0 | 平均から 2 標準偏差以上の逸脱 |
| 重大閾値 | Z > 3.0 | 平均から 3 標準偏差以上の逸脱 |
| 絶対上限 | > 70℃ | Z-score に関わらず即座にアラート |
| 評価対象 | 同一 equipment_id | 設備単位でベースラインを計算 |

```sql
-- 温度スパイク検出クエリ
WITH temp_stats AS (
    SELECT
        equipment_id,
        AVG(temperature) AS avg_temp,
        STDDEV(temperature) AS std_temp
    FROM silver.production_facts
    WHERE production_date >= DATE_ADD(CURRENT_DATE(), -30)
    GROUP BY equipment_id
)
SELECT
    f.production_date,
    f.equipment_id,
    f.temperature,
    s.avg_temp,
    s.std_temp,
    (f.temperature - s.avg_temp) / NULLIF(s.std_temp, 0) AS z_score,
    CASE
        WHEN f.temperature > 70 THEN 'CRITICAL_ABSOLUTE'
        WHEN (f.temperature - s.avg_temp) / NULLIF(s.std_temp, 0) > 3.0 THEN 'CRITICAL'
        WHEN (f.temperature - s.avg_temp) / NULLIF(s.std_temp, 0) > 2.0 THEN 'WARNING'
        ELSE 'NORMAL'
    END AS alert_level
FROM silver.production_facts f
JOIN temp_stats s ON f.equipment_id = s.equipment_id
WHERE f.production_date = DATE_ADD(CURRENT_DATE(), -1);
```

### 4.2 振動トレンド検出

振動値の緩やかな上昇トレンドを検出し、ベアリング摩耗や回転体の偏心を予兆段階で発見する。

| パラメータ | 値 | 説明 |
|-----------|-----|------|
| 検出方法 | 線形回帰の傾き | 過去 14 日間の振動値に対する回帰分析 |
| 警告閾値 | 傾き > 0.05 mm/s/日 | 2 週間で約 0.7 mm/s の上昇 |
| 重大閾値 | 傾き > 0.10 mm/s/日 | 2 週間で約 1.4 mm/s の上昇 |
| 最小サンプル | 7 日以上 | 信頼性のある回帰分析のため |
| 評価対象 | 同一 equipment_id | 設備単位でトレンドを評価 |

```sql
-- 振動トレンド検出（簡易版: 7日移動平均の比較）
WITH vibration_ma AS (
    SELECT
        equipment_id,
        production_date,
        vibration,
        AVG(vibration) OVER (
            PARTITION BY equipment_id
            ORDER BY production_date
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ) AS ma_7day,
        AVG(vibration) OVER (
            PARTITION BY equipment_id
            ORDER BY production_date
            ROWS BETWEEN 13 PRECEDING AND 7 PRECEDING
        ) AS ma_prev_7day
    FROM silver.production_facts
    WHERE production_date >= DATE_ADD(CURRENT_DATE(), -21)
)
SELECT
    equipment_id,
    MAX(production_date) AS latest_date,
    ROUND(AVG(ma_7day), 3) AS current_avg,
    ROUND(AVG(ma_prev_7day), 3) AS previous_avg,
    ROUND(AVG(ma_7day) - AVG(ma_prev_7day), 3) AS trend_change,
    CASE
        WHEN AVG(ma_7day) - AVG(ma_prev_7day) > 0.7 THEN 'CRITICAL'
        WHEN AVG(ma_7day) - AVG(ma_prev_7day) > 0.35 THEN 'WARNING'
        ELSE 'NORMAL'
    END AS alert_level
FROM vibration_ma
WHERE production_date >= DATE_ADD(CURRENT_DATE(), -7)
GROUP BY equipment_id;
```

### 4.3 不良率急増検出

不良率の急激な増加を検出し、原材料の品質問題や設備の調整不良を早期に発見する。

| パラメータ | 値 | 説明 |
|-----------|-----|------|
| 不良率の計算 | `defect_quantity / actual_quantity * 100` | 実績数量に対する不良数量の割合 |
| 検出方法 | 前日比 + 移動平均比較 | 急激な変化と緩やかな悪化の両方を検出 |
| 絶対警告閾値 | 不良率 > 5% | 業界基準の上限 |
| 絶対重大閾値 | 不良率 > 10% | 即座にライン停止を検討 |
| 相対警告閾値 | 前日比 +3% ポイント | 急激な悪化 |
| 評価対象 | line_id + product_code 単位 | ライン・製品の組み合わせで評価 |

```sql
-- 不良率急増検出クエリ
WITH defect_rates AS (
    SELECT
        production_date,
        line_id,
        product_code,
        SUM(defect_quantity) AS total_defects,
        SUM(actual_quantity) AS total_actual,
        ROUND(SUM(defect_quantity) / NULLIF(SUM(actual_quantity), 0) * 100, 2)
            AS defect_rate,
        LAG(
            ROUND(SUM(defect_quantity) / NULLIF(SUM(actual_quantity), 0) * 100, 2)
        ) OVER (
            PARTITION BY line_id, product_code
            ORDER BY production_date
        ) AS prev_day_defect_rate
    FROM silver.production_facts
    WHERE production_date >= DATE_ADD(CURRENT_DATE(), -14)
    GROUP BY production_date, line_id, product_code
)
SELECT
    production_date,
    line_id,
    product_code,
    defect_rate,
    prev_day_defect_rate,
    ROUND(defect_rate - COALESCE(prev_day_defect_rate, 0), 2) AS rate_change,
    CASE
        WHEN defect_rate > 10 THEN 'CRITICAL_ABSOLUTE'
        WHEN defect_rate > 5 THEN 'WARNING_ABSOLUTE'
        WHEN defect_rate - COALESCE(prev_day_defect_rate, 0) > 3 THEN 'WARNING_SPIKE'
        ELSE 'NORMAL'
    END AS alert_level
FROM defect_rates
WHERE production_date = DATE_ADD(CURRENT_DATE(), -1);
```

## 5. 品質スコア算出

### 5.1 算出方式

6 次元の検証結果を加重平均して、0〜100 点の品質スコアを算出する。

**計算式**:

```
品質スコア = Σ(次元スコア_i × 重み_i) / Σ(重み_i) × 100
```

**各次元の重みと計算方法**:

| # | 品質次元 | 重み | スコアの計算方法 |
|---|---------|------|----------------|
| 1 | 完全性 | 1.0 | `(全カラムの非 NULL 率の加重平均)` |
| 2 | 正確性 | 1.0 | `(範囲内レコード数 + マスタ照合成功数) / (チェック対象レコード総数)` |
| 3 | 一貫性 | 0.8 | `(整合性ルール通過レコード数) / (チェック対象レコード総数)` |
| 4 | 適時性 | 0.8 | `SLA 内到達なら 1.0、超過時間に応じて減点` |
| 5 | 一意性 | 1.0 | `(ユニークレコード数) / (全レコード数)` |
| 6 | 有効性 | 0.8 | `(Enum + フォーマット + 型チェック通過数) / (チェック対象総数)` |

**合計重み**: 1.0 + 1.0 + 0.8 + 0.8 + 1.0 + 0.8 = **5.4**

### 5.2 算出例

```
完全性:  0.98 × 1.0 = 0.98
正確性:  0.95 × 1.0 = 0.95
一貫性:  0.99 × 0.8 = 0.792
適時性:  1.00 × 0.8 = 0.80
一意性:  0.97 × 1.0 = 0.97
有効性:  0.96 × 0.8 = 0.768

品質スコア = (0.98 + 0.95 + 0.792 + 0.80 + 0.97 + 0.768) / 5.4 × 100
           = 5.26 / 5.4 × 100
           = 97.4 点 → グレード A
```

### 5.3 グレード判定

| グレード | スコア範囲 | ラベル | 対応アクション |
|---------|-----------|-------|-------------|
| A | 95 以上 | 優秀 | 定常監視を継続。追加対応不要 |
| B | 85 以上 95 未満 | 良好 | 週次レポートで報告。悪化トレンドがあれば原因調査 |
| C | 70 以上 85 未満 | 要注意 | 品質管理担当に通知。1 週間以内に改善計画を策定 |
| D | 50 以上 70 未満 | 要改善 | データ利用者に品質低下を通知。ダッシュボードに警告表示 |
| F | 50 未満 | 重大 | パイプライン停止。エスカレーション。緊急対応チームを招集 |

## 7. 違反時の処理フロー（Quarantine パターン）

品質違反が発生した場合のデータフローを以下に示す。

```
入力データ
  │
  ▼
┌──────────────┐
│ 品質チェック  │
│  (6次元)     │
└──────┬───────┘
       │
  ┌────┴────┐
  │         │
  ▼         ▼
[PASS]    [FAIL]
  │         │
  ▼         ▼
┌──────┐  ┌─────────────────────────────────────┐
│Silver│  │ quarantine.production_facts_errors   │
│Table │  │ ┌─────────────────────────────────┐ │
└──────┘  │ │ + violation_type                │ │
          │ │ + violated_rule                 │ │
          │ │ + violated_column               │ │
          │ │ + original_value                │ │
          │ │ + detected_at                   │ │
          │ │ + pipeline_run_id               │ │
          │ └─────────────────────────────────┘ │
          └─────────────────┬───────────────────┘
                            │
                   ┌────────┴────────┐
                   │ 手動レビュー     │
                   │ (品質管理担当)   │
                   └────────┬────────┘
                            │
                  ┌─────────┴─────────┐
                  │                   │
                  ▼                   ▼
             [修正可能]          [修正不可]
                  │                   │
                  ▼                   ▼
          ┌──────────┐         ┌──────────┐
          │データ修正 │         │廃棄ログ  │
          │→ 再投入  │         │記録      │
          └──────────┘         └──────────┘
```

**原則**: エラーデータは削除しない。quarantine テーブルに分離し、調査と修正が完了した後に再投入する。

## 8. 実装チェックリスト

### 品質ルール実装時

- [ ] 6 次元（完全性, 正確性, 一貫性, 適時性, 一意性, 有効性）すべてのルールを実装したか
- [ ] quality-rules.yaml の定義と実装コードが一致しているか
- [ ] quarantine テーブルのスキーマにメタデータカラムを含めたか
- [ ] エラー率の閾値（10%）でパイプライン停止ロジックを実装したか

### 品質ゲート実装時

- [ ] Bronze → Silver ゲート（スキーマ + 完全性 + 一意性 + 有効性 + 適時性）を実装したか
- [ ] Silver → Gold ゲート（全 6 次元 + 品質スコア算出）を実装したか
- [ ] ゲート不通過時に quarantine テーブルへの分離が動作するか
- [ ] 品質スコアのログ出力（構造化 JSON）を実装したか

### 異常検知実装時

- [ ] 温度スパイク検出クエリが正しく動作するか
- [ ] 振動トレンド検出クエリが正しく動作するか
- [ ] 不良率急増検出クエリが正しく動作するか
- [ ] 異常検知結果のアラート通知が設定されているか

### ダッシュボード実装時

- [ ] 品質スコア（KPI カード）が表示されるか
- [ ] 6 次元レーダーチャートが表示されるか
- [ ] 品質スコア推移グラフ（過去 30 日）が表示されるか
- [ ] 異常検知アラートが表示されるか
- [ ] quarantine レコードへのドリルダウンが可能か
