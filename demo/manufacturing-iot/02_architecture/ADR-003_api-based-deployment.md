# ADR-003: Fabric への配置を REST API と生成した定義ファイルで自動化する

| 項目 | 値 |
|------|-----|
| ステータス | 承認済 |
| 作成日 | 2026-10-30 |
| 作成者 | 猪野 勉 / Claude AI |
| 影響範囲 | 製造業 IoT デモ — `08_fabric/automation/`、`08_fabric/powerbi/` |
| 関連ADR | MFG-002（Direct Lake）、TFSE-009（ルールのプロジェクト単位配布） |

## 1. コンテキスト（必須）

デモを Fabric の試用環境に配置する手順（`08_fabric/deploy-guide.md` 手順 2〜9）は、GUI で行うと 2〜3 時間かかり、作業者によって結果がばらつく。

| 状況 | 内容 |
|------|------|
| 試用期間 | Fabric 試用版は 60 日で終わるため、提案やデモのたびに環境を作り直す可能性がある |
| 一貫性 | セマンティックモデルのメジャー（80 個）とレポート（3 ページ）は設計書（`powerbi/`）と一致している必要がある |
| テナント設定 | 検証したテナントでは「レポートの画像エクスポート」が無効で、ExportTo API が使えなかった（組織全体の設定のため、デモのために変えない） |

## 2. 決定（必須）

1. **配置は Fabric / OneLake / Power BI の REST API で行う**。ワークスペース・Lakehouse・Notebook・セマンティックモデル・レポート・Data Pipeline を、同名があれば更新する形で作成する
2. **セマンティックモデル（TMDL）は設計書から生成する**。`powerbi/dax-measures.dax`（式）と `dax-measures.md`（書式・表示フォルダー）と、Lakehouse の実テーブル定義を入力にする。設計書を唯一の正とする
3. **レポート（PBIR）は `powerbi/dashboard-spec.md` に沿った定義をスクリプトで生成する**
4. **画面キャプチャは、Power BI の JavaScript ライブラリでレポートを埋め込み表示して撮る**（ExportTo API は使わない）
5. 認証は Azure CLI の委任トークンを使い、ファイルやコマンドラインに秘密情報を残さない

## 3. 理由

### 検討した代替案

| 案 | 概要 | 不採用理由 |
|----|------|-----------|
| **REST API ＋ 生成（採用）** | 定義を生成して API で配置する | — |
| GUI の手作業 | 手順書どおりに画面で作る | 再現性がなく、2〜3 時間かかる。メジャーの書式や表示フォルダーの設定漏れが起きやすい |
| Fabric の Git 統合 ＋ デプロイ パイプライン | ワークスペースをリポジトリと同期し、ステージ間で昇格する | 本番運用には適するが、まっさらな環境の立ち上げや試用環境の作り直しには、Git プロバイダーとの接続などの準備が多い。定義ファイル（TMDL / PBIR）はいずれにせよ必要 |
| fabric-cicd（Microsoft の Python ライブラリ） | 項目定義のフォルダーを配置する | 有力な選択肢。今回は設計書からの定義生成が中心で、配置部分は小さいため採用しなかった。本番化の際は再検討する |
| Terraform の Fabric プロバイダー | 基盤をコード化する | ワークスペース・容量などの基盤には適するが、モデルやレポートの中身の生成は別途必要 |
| 画面キャプチャを ExportTo API で撮る | Power BI の画像エクスポート | テナント設定（組織全体）を変える必要がある。埋め込み表示なら設定を変えずに撮れる |

### 採用理由

- 試用環境を 30 分程度で作り直せる（30 日分の処理を含む）
- 設計書を変更すれば、モデルとレポートに確実に反映される（手作業による不一致がない）
- 同名の項目は更新するため、何度実行しても重複しない

## 4. 結果・影響

| 観点 | 影響 |
|------|------|
| ✅ 再現性 | 2026-10-30 に既存環境に対して通し実行し、検証 13 項目・メジャー 80 個がすべて期待どおりだった |
| ✅ 設計書との一致 | 生成した TMDL・レポート定義は、手作業で配置したものと一致した（lineageTag を除く） |
| ⚠️ 定義形式への依存 | TMDL / PBIR の形式や API の仕様変更に追随する必要がある。PBIR 形式の提供状況は採用前に最新情報を確認する |
| ⚠️ 生成スクリプトの保守 | 設計書（Markdown）の書き方が変わると、メジャーの読み取りが壊れる。単体テストで読み取り規則を固定する |
| ⚠️ 品質の担保 | 初版は実環境での通し実行だけで確認しており、コードレビューで状態管理・タイムアウト・トークンの扱いなどに不備が見つかった（2026-10-30）。テスト先行で書き直す |
| ⚠️ 権限 | 実行者の委任権限で動く。共有環境では専用アカウントやサービスプリンシパルの利用を検討する |

### 再検討の条件

- 顧客の本番環境に展開する場合（Git 統合 ＋ デプロイ パイプライン、または fabric-cicd を優先する）
- Fabric の公式ツールで、設計書からの生成を含めて同等のことができるようになった場合
