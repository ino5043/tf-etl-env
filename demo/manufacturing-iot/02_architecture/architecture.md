## 2. パイプラインパターン選択

### 選択: 日次バッチ ETL + パーティションオーバーライト

| 判断項目 | 結論 | 根拠 |
|---------|------|------|
| パターン | **ETL（Extract → Transform → Load）** | ✅確定: データ品質を事前保証してからロード |
| 実行タイミング | 日次 AM 4:00〜5:00 JST | ⚡推論: ソース出力 AM 3:00、SLA AM 8:00 から逆算 |
| 冪等性方式 | パーティションオーバーライト（`replaceWhere`） | ⚡推論: 全件洗替のため MERGE 不要 |
| オーケストレータ | Fabric Pipeline | ✅確定: Fabric 環境、追加コスト不要 |

### パターン選択の判断プロセス

```
リアルタイム処理が必要？ → NO（日次バッチで十分）
差分データのみ処理で十分？ → NO（全件洗替のため差分不可）
ターゲット側に計算リソースがある？ → YES だが...
データ品質を事前保証したい？ → YES → ETL + 品質ゲート を選択
```

> 詳細な代替案比較は `ADR-001_pipeline-pattern.md` を参照。

### 3.2 Bronze 層: 生データ取り込み

**テーブル**: `bronze.raw_production`

| 項目 | 設計 |
|------|------|
| 目的 | CSV ファイルの忠実な保存（変換なし） |
| 書き込み方式 | パーティションオーバーライト（`production_date` 単位） |
| パーティションキー | `_batch_date`（取り込み対象日） |
| メタカラム | `_ingestion_timestamp`, `_source_file`, `_batch_id`, `_batch_date` |
| スキーマ | すべて STRING 型（ソースそのまま） |
| 保持期間 | 3 年（再処理用） |

**Bronze 取り込みの冪等性方式**:

```python
# 全件洗替のため、日付パーティション単位で上書き
df.write \
    .format("delta") \
    .mode("overwrite") \
    .option("replaceWhere", f"_batch_date = '{target_date}'") \
    .saveAsTable("bronze.raw_production")
```

> ⚡推論: ソースが全件洗替のため、Append Only ではなくパーティションオーバーライトを採用。
> 同日の再実行でデータ重複を防ぐ。Bronze の「変換しない」原則は維持。

## 4. エラーハンドリング戦略

### 4.1 品質ゲート

#### 品質ゲート 1: Bronze → Silver

| チェック項目 | 閾値 | 失敗時の動作 |
|-------------|------|-------------|
| レコード件数 | > 0 件 | パイプライン停止 + アラート |
| 必須カラム NOT NULL 率 | >= 99% | 品質違反レコードを Dead Letter Table へ分離 |
| 数値型変換成功率 | >= 99% | 変換失敗レコードを Dead Letter Table へ分離 |
| 日付型変換成功率 | = 100% | パイプライン停止 + アラート |
| 温度範囲チェック（-10〜200℃） | 違反 < 1% | 範囲外レコードを Dead Letter Table へ分離 |
| 振動範囲チェック（0〜50 mm/s） | 違反 < 1% | 範囲外レコードを Dead Letter Table へ分離 |
| 全体エラー率 | < 1% | 超過時はパイプライン停止 + アラート |

#### 品質ゲート 2: Silver → Gold

| チェック項目 | 閾値 | 失敗時の動作 |
|-------------|------|-------------|
| Silver テーブル件数 | > 0 件 | パイプライン停止 |
| 集計整合性 | Silver SUM = Gold SUM | 不一致でパイプライン停止 |
| KPI 妥当性（defect_rate） | 0〜100% | 範囲外でアラート（停止はしない） |
| KPI 妥当性（achievement_rate） | 0〜200% | 範囲外でアラート |

### 4.2 Dead Letter Table

**テーブル**: `meta.dead_letter_production`

| カラム名 | 型 | 説明 |
|---------|-----|------|
| `error_id` | STRING | エラーレコード一意ID |
| `batch_id` | STRING | バッチID |
| `process_date` | DATE | 処理対象日 |
| `source_table` | STRING | エラー発生元テーブル |
| `error_type` | STRING | エラー種別（NULL_VIOLATION, TYPE_CAST_ERROR, RANGE_VIOLATION） |
| `error_column` | STRING | エラー発生カラム |
| `error_value` | STRING | エラー値（元の値） |
| `error_message` | STRING | エラー詳細メッセージ |
| `original_record` | STRING | 元レコード全体（JSON） |
| `created_at` | TIMESTAMP | エラー記録日時 |
| `resolved` | BOOLEAN | 解決済みフラグ |
| `resolved_at` | TIMESTAMP | 解決日時 |

### 4.3 リトライ戦略

| エラー種別 | リトライ | 待機時間 | 対応 |
|-----------|---------|---------|------|
| CSV ファイル未着 | 3 回 | 15 分間隔 | AM 5:00 までに未着ならアラート |
| Blob Storage 接続エラー | 3 回 | 指数バックオフ（2, 4, 8 分） | 自動リトライ |
| Spark ジョブ失敗 | 2 回 | 5 分間隔 | 自動リトライ後、手動対応 |
| データ品質違反（< 1%） | 0 回 | - | Dead Letter Table へ分離して続行 |
| データ品質違反（>= 1%） | 0 回 | - | パイプライン停止 + アラート |
| スキーマ変更検出 | 0 回 | - | パイプライン停止 + 手動対応 |

### 4.4 アラート設計

| アラート条件 | 重要度 | 通知先 | 通知方法 |
|-------------|--------|--------|---------|
| CSV ファイル未着（AM 5:00） | CRITICAL | 生産管理課 + データチーム | Teams + メール |
| エラー率 >= 1% | CRITICAL | データチーム | Teams + メール |
| エラー率 >= 0.5% | WARNING | データチーム | Teams |
| パイプライン AM 7:30 未完了 | CRITICAL | データチーム | Teams + メール |
| 設備異常検出（温度/振動逸脱） | WARNING | 設備保全チーム | Teams |
| 不良率 > 5% | WARNING | 品質管理担当 | Teams |

## 5. パイプラインスケジュール

### DAG 設計

```
AM 3:00  CSV ファイル出力（MES）
  │
  ▼
AM 4:00  [bronze_ingest] CSV → Bronze
  │       Fabric Pipeline: Notebook Activity
  │       タイムアウト: 15 分 / リトライ: 3 回
  ▼
AM 4:30  [silver_transform] Bronze → Silver
  │       Fabric Pipeline: Notebook Activity
  │       タイムアウト: 30 分 / リトライ: 2 回
  │
  ├──→ [silver_equipment_scd] Bronze → Silver (SCD2)
  │       タイムアウト: 15 分 / リトライ: 2 回
  ▼
AM 5:30  [gold_aggregate] Silver → Gold
  │       Fabric Pipeline: Notebook Activity
  │       タイムアウト: 30 分 / リトライ: 1 回
  ▼
AM 6:00  [semantic_model_refresh] Gold → Power BI
  │       Fabric Pipeline: Semantic Model Refresh
  │       タイムアウト: 30 分 / リトライ: 1 回
  ▼
AM 7:00  完了（SLA AM 8:00 に対して 1 時間のバッファ）
```

### 依存関係定義

```yaml
# pipeline-dependencies.yaml
pipelines:
  bronze_ingest:
    schedule: "0 4 * * *"  # JST AM 4:00
    depends_on: []
    timeout: 15m
    retries: 3
    retry_interval: 15m

  silver_transform:
    schedule: null  # 前段完了トリガー
    depends_on:
      - bronze_ingest
    timeout: 30m
    retries: 2
    retry_interval: 5m

  silver_equipment_scd:
    schedule: null
    depends_on:
      - bronze_ingest
    timeout: 15m
    retries: 2
    retry_interval: 5m

  gold_aggregate:
    schedule: null
    depends_on:
      - silver_transform
      - silver_equipment_scd
    timeout: 30m

  semantic_model_refresh:
    schedule: null
    depends_on:
      - gold_aggregate
    timeout: 30m

```

### 確認事項 3: 設備マスター

- [ ] 設備マスターは CSV から生成する方針でよいか？（別途マスター管理があるか）
- [ ] SCD Type 2 で設備状態の履歴管理は必要か？（保全チームに確認）

### 確認事項 4: パイプラインスケジュール

- [ ] AM 4:00 開始で問題ないか？（CSV 出力 AM 3:00 からのバッファ 1 時間）
- [ ] 休日・祝日の運用方針は？（工場の稼働カレンダーに合わせるか）
- [ ] 月初・期末の特殊処理は必要か？
