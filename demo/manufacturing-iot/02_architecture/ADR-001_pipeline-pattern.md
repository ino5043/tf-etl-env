# ADR-001: データ取り込み方式の選択

| 項目 | 値 |
|------|-----|
| ステータス | 承認済 |
| 作成日 | 2026-03-15 |
| 作成者 | Claude AI（pipeline-architect agent） |
| 影響範囲 | 製造業 IoT デモ — 全パイプライン |
| 関連ADR | なし（初回 ADR） |

## 1. コンテキスト（必須）

工場の製造実行システム（MES）から出力される日次 CSV ファイル（生産実績 + センサーデータ）を Azure Fabric Lakehouse に取り込む方式を決定する必要がある。

### 現状と背景

- MES が毎日 AM 3:00 に前日分の CSV ファイル（`production_YYYYMMDD.csv`）を出力する
- ファイル形式は UTF-8 BOM 付き、CRLF 改行、ヘッダー行あり
- データ量は日次 500〜1,000 件（約 500KB）で、月 +3% の成長率
- **更新パターンは「全件洗替」**（差分ではなく、対象日の全レコードを再出力する）
- 工場長が毎朝 **AM 8:00 JST** に Power BI ダッシュボードで前日データを確認する

### 制約条件

| 制約 | 詳細 |
|------|------|
| プラットフォーム | Microsoft Fabric（F2 容量、月額固定） |
| SLA | AM 8:00 JST にデータ参照可能 |
| 可用性 | 99.5% |
| エラー率 | < 1% |
| チームスキル | Python ○, SQL ○, PySpark △（学習中） |
| データ分類 | 社外秘 |
| 予算 | Fabric F2 容量内で収める（追加サービス不可） |

### 解決すべき問題

1. CSV ファイルを Lakehouse に確実に取り込み、AM 8:00 までにダッシュボードに反映する方式の選択
2. データ品質を保証しながら、Fabric F2 の容量制約内で運用可能な設計
3. PySpark 初心者でも保守可能なシンプルな構成

## 2. 決定（必須）

**日次バッチ ETL（Extract → Transform → Load）** を採用する。

具体的な構成:

| 項目 | 決定内容 |
|------|---------|
| パイプラインパターン | ETL（変換後にロード） |
| 実行頻度 | 日次 1 回（AM 4:00 JST 開始） |
| 冪等性方式 | パーティションオーバーライト（`replaceWhere` 句） |
| レイヤー構成 | Medallion Architecture（Bronze → Silver → Gold） |
| オーケストレータ | Fabric Pipeline |
| 実行エンジン | Fabric Notebook（PySpark） |
| 品質管理 | レイヤー間に品質ゲートを設置 |
| エラー処理 | Dead Letter Table にエラーレコードを分離 |

### 冪等性の実現方法

ソースが「全件洗替」であるため、日付パーティション単位のオーバーライトで冪等性を実現する。

```python
# 同日の再実行でもデータが重複しない
df.write \
    .format("delta") \
    .mode("overwrite") \
    .option("replaceWhere", f"process_date = '{target_date}'") \
    .saveAsTable("target_table")
```

## 3. 理由

### 選択理由

1. **データ量が小さい**: 日次 500〜1,000 件 / 500KB はバッチ処理で十分処理可能
2. **リアルタイム性不要**: SLA が AM 8:00 であり、AM 3:00 出力から 5 時間のバッファがある
3. **全件洗替**: ソースが差分ではなく全件出力のため、CDC は適用不可
4. **チームスキル**: PySpark 初心者でも理解しやすいバッチ処理が最適
5. **コスト**: Fabric F2 容量内で完結し、追加サービスが不要
6. **品質保証**: ETL パターンにより、ロード前にデータ品質を検証できる

### 検討した代替案と不採用理由

#### 代替案 1: CDC（Change Data Capture）

| 観点 | 評価 |
|------|------|
| 概要 | MES の DB から変更データのみをキャプチャして伝搬 |
| 不採用理由 | ソースが CSV ファイル出力（全件洗替）のため、CDC の前提条件（DB の変更ログ）を満たさない |
| 追加リスク | MES 側の DB アクセス権取得が必要で、既存システムへの影響リスク |

#### 代替案 2: 時間単位バッチ（毎時処理）

| 観点 | 評価 |
|------|------|
| 概要 | 1 時間ごとに CSV の到着をチェックして取り込み |
| 不採用理由 | ソースが日次 1 回出力のため、23 時間は空振りになる。Fabric 容量の無駄遣い |
| 追加リスク | パイプライン実行回数増による運用監視の負荷増 |

#### 代替案 3: Event Hub + Eventstream（ストリーミング）

| 観点 | 評価 |
|------|------|
| 概要 | MES からリアルタイムでイベントを受信し、Eventstream で処理 |
| 不採用理由 | (1) MES がリアルタイム出力に非対応（CSV バッチ出力のみ）、(2) F2 容量でストリーム処理は高負荷、(3) チームの PySpark スキルが不足 |
| 追加リスク | Eventstream の追加コスト、24/365 稼働のモニタリング負荷 |

#### 代替案 4: ELT（Load 後に Transform）

| 観点 | 評価 |
|------|------|
| 概要 | CSV をそのまま Lakehouse にロードし、SQL / Spark で後から変換 |
| 不採用理由 | データ品質を事前保証したい要件（エラー率 < 1%）に対し、ロード後の品質問題発見では手戻りが大きい |
| 備考 | 技術的には可能だが、品質ゲートを Bronze → Silver 間に置くことで ETL パターンと同等の効果を得られるため、明示的に ETL と定義 |

### 比較表

| 観点 | 日次バッチ ETL | CDC | 時間単位バッチ | ストリーミング | ELT |
|------|:---:|:---:|:---:|:---:|:---:|
| コスト | ◎ | △ | ○ | ✕ | ◎ |
| シンプルさ | ◎ | △ | ○ | ✕ | ◎ |
| データ品質保証 | ◎ | ○ | ◎ | ○ | △ |
| データ鮮度 | △ | ◎ | ○ | ◎ | △ |
| チーム対応力 | ◎ | △ | ○ | ✕ | ◎ |
| Fabric F2 適合性 | ◎ | △ | ○ | ✕ | ◎ |
| ソース適合性 | ◎ | ✕ | △ | ✕ | ◎ |

**凡例**: ◎ 最適 / ○ 可 / △ 課題あり / ✕ 不適合

**総合判断**: 日次バッチ ETL

**決定的な理由**: ソースが CSV 全件洗替（日次 1 回出力）であるため、CDC・ストリーミングは技術的に不適合。残る ETL と ELT の比較では、データ品質の事前保証（品質ゲート）を重視し ETL を選択。

## 4. 結果・影響

| 観点 | 影響 |
|------|------|
| ✅ コスト | Fabric F2 容量内で完結。追加サービス不要 |
| ✅ シンプルさ | Notebook 4 本 + Pipeline 1 本のシンプル構成。PySpark 初心者でも保守可能 |
| ✅ 品質保証 | Bronze → Silver 間の品質ゲートで、ロード前にデータ品質を検証可能 |
| ✅ 冪等性 | パーティションオーバーライトにより、再実行が安全。障害復旧が容易 |
| ✅ 運用負荷 | 日次 1 回の実行のみ。モニタリング対象が少ない |
| ⚠️ データ鮮度 | 最大 24 時間の遅延（当日データは翌日 AM 8:00 に反映） |
| ⚠️ リアルタイム対応 | 設備異常の即時検知は不可（翌日のダッシュボードで確認） |
| ⚠️ スケーラビリティ | データ量が 10 万件/日を超えた場合、処理時間が SLA を圧迫する可能性 |

### 将来の再検討条件

以下の条件が変化した場合、本 ADR の見直しが必要:

1. **リアルタイム要件の追加**: 設備異常を即時検知したい場合 → ストリーミングへの移行を検討
2. **データ量の急増**: 月 +3% を大幅に超える成長（10 万件/日超） → マイクロバッチまたは ELT への移行を検討
3. **MES のリアルタイム出力対応**: CSV 以外の出力方式（API, DB 直接接続）が可能になった場合 → CDC を検討
4. **Fabric 容量のアップグレード**: F4 以上への移行時 → ストリーミング処理の導入を検討
